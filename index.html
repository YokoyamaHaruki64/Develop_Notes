    ホーム/Class Design

    Class Design

    目的

    この資料では、クラスの概念設計・ホワイトボード設計を行う。

    この段階で決めるのは主に次の内容。

    • クラスの責務
    • 何を所有し、何を参照するか
    • 主要なメンバ構成
    • 外部へ公開する主要 API
    • 他クラスとの大まかな関係
    • 必要なら処理の流れ

    「安全に完成させるための設計」ではなく、今考えるために必要な最小限の設計を優先する。

    基本方針

    設計順は原則として次の順番にする。

    1. 責務を決める
    2. 所有するもの・参照するものを決める
    3. 主要なメンバを置く
    4. Public API を決める
    5. 各 API がどのメンバを操作するか確認する
    6. 責務が明確に独立している場合だけ内部クラスや Subsystem に分割する
    7. 必要になった段階で保証・エラー処理・安全性を追加する

    最初から完成形を目指さない。

    この段階では原則として入れないもの

    明確な要求がない限り、以下を設計へ追加しない。

    • Thread Safety
    • 例外安全性
    • 不正な呼び出し順への完全な対策
    • 厳密なライフタイム保証
    • Validation 層
    • Result / Expected 型
    • Factory
    • 抽象 Interface
    • 過剰な RAII Wrapper
    • 世代管理や複雑な Handle 管理
    • 将来の拡張だけを理由にした抽象化
    • 「念のため」の Manager / Service / Adapter
    • エラー状態を完全に表現するためだけの状態機械

    これらが将来的に必要そうでも、現在の責務や API を考えるために不要なら保留する。

    分割ルール

    クラスを分割するのは、責務が明確に独立している場合だけ。

    「将来大きくなりそう」 「テストしやすそう」 「安全性を保証しやすそう」

    だけを理由に分割しない。

    まず単純な 1 クラスとして形を出し、そこから責務が自然に分かれる場合だけ分割する。

    不明点の扱い

    不明点を新しい抽象化で解決しない。

    判断材料が不足している場合は、

    • TBD
    • 要検討
    • 仮置き

    として残してよい。

    未決定事項を無理に確定させるより、現在確定している構造を明確にすることを優先する。

    クラスごとの記述形式

    クラス設計Markdownの具体的な記述形式は Class/_FormatTemplate.md に従う。

    C++識別子の命名は NamingConvention.md に従う。

    コード例

    class Renderer
{
public:
    bool Initialize(...);
    void Shutdown();

    void BeginFrame();
    void Submit(const RenderItem& item);
    void Render();
    void Present();

private:
    Device* m_device = nullptr;

    RenderQueue m_renderQueue;
    FrameContext m_frames[FrameCount];

    uint32_t m_frameIndex = 0;
};

    この段階では、

    • Present() が二重に呼ばれた場合
    • Submit() 中に別スレッドからアクセスされた場合
    • Device Lost
    • Shutdown 中のアクセス
    • すべての API の戻り値設計

    などを先回りして解決しない。

    まず Renderer が何を持ち、外から何をさせるクラスなのかを決める。

    AI / Codex 向け指示

    以下をクラス設計時の基本指示として使用する。

    クラスの概念設計・ホワイトボード設計を行ってください。

    目的は、責務・所有関係・主要メンバ・主要な Public API を決めることです。

    現段階では完成形や堅牢性を求めません。 「実運用上必要な最低限」ではなく、「現在の構造を考えるために必要な最低限」を提示してください。

    明確に要求されていない限り、Thread Safety、例外安全性、不正呼び出し対策、厳密なライフタイム保証、Validation、Result 型、Factory、抽象 Interface、過剰な RAII Wrapper、将来拡張のためだけの抽象化を追加しないでください。

    不明点は新しい層や仕組みを追加して解決せず、TBD または要検討として残してください。

    まず単純な 1 クラスとして考え、責務が明確に独立する場合だけ分割してください。

    出力では、各クラスについて最低限以下を示してください。

    • 責務
    • 所有するもの / 参照するもの
    • 主要メンバ
    • Public API
    • 他クラスとの関係
    • 未決定事項

    実装コードは不要です。必要なら API とメンバが分かる C++ のクラス宣言だけ示してください。

    ホーム/Naming Convention

    Naming Convention

    HestiaEngineで使用する名前空間とC++識別子の命名規約。 必要なルールだけを定義し、細かすぎる規約は必要になった時点で追加する。

    Namespace

    Hestia

    Engine.dll内部の型、およびGame.dllとのDLL境界で共有する型は Hestia 名前空間に置く。

    Hestia::Engine
Hestia::Time
Hestia::TimeAPI
Hestia::AssetHandle

    Subsystemごとの細かい名前空間は原則作らない。

    // 原則避ける
Hestia::Engine::Graphics::Resource::Texture

    HestiaGame

    Game.dll側でGame Scriptへ公開するstatic Facadeは HestiaGame 名前空間に置く。

    HestiaGame::Time
HestiaGame::Assets
HestiaGame::Graphics

    Script専用共通Headerでは、Game Scriptから利用する共有型とFacadeを簡潔に扱うため、以下を使用してよい。

    using namespace Hestia;
using namespace HestiaGame;

    Engine内部実装型はGame.dll向け共有Headerへ公開しないため、同名のEngine内部型とGame FacadeがScript側で衝突しない構成とする。

    Identifier

    対象 形式 例
    Namespace UpperCamel HestiaGame
    Class / Struct UpperCamel GraphicsSystem
    Type Alias UpperCamel EntityID
    Enum UpperCamel RenderPhase
    Enum Value UpperCamel Transparent
    Function UpperCamel SetTimeScale()
    Constant UPPER_SNAKE_CASE MAX_ENTITY_COUNT
    Macro UPPER_SNAKE_CASE HESTIA_EDITOR
    Member Variable m_lowerCamel m_timeScale
    Static Member Variable s_lowerCamel s_instance
    Local Variable lowerCamel deltaTime
    Parameter lowerCamel timeScale
    File Name UpperCamel GraphicsSystem.h

    const や constexpr であっても、一時的なローカル変数は通常の lowerCamel とする。 名前付きの定数として定義するものは UPPER_SNAKE_CASE とする。

    API Table

    APIテーブル内の公開関数ポインタは、データメンバではなく公開関数相当として扱い、関数名と同じ UpperCamel を使用する。

    struct EngineAPI
{
    Engine* (*Create)(const ApplicationAPI*);
    void (*Destroy)(Engine*);
    void (*FrameExecute)(Engine*, float);
};

    APIテーブル内部で保持するContextやCallbackなど、実装用の通常メンバは m_lowerCamel を使用する。

    ホーム/Subsystem / Boundary API / Game Facade Design

    Subsystem / Boundary API / Game Facade Design

    目的

    Engine内部のSubsystemを直接Game.dllへ公開せず、DLL境界では必要な機能だけを XxxAPI として公開する。 Engine側および境界共有型は Hestia、Game Script向けFacadeは HestiaGame 名前空間を使用する。

    設計上は次の3層に分ける。

    Engine内部実装
    XxxSystem
        ↓
DLL境界公開面
    XxxAPI
        ↓
Game.dll向けFacade
    HestiaGame::Xxx

    1. Subsystem

    SubsystemはEngine内部の本体であり、状態・実装・管理処理を保持する。

    class AssetSystem
{
public:
    static AssetHandle Load(AssetID id);
    static bool IsLoaded(AssetHandle handle);

    AssetInfo GetDetailedInfo(AssetHandle handle) const;

    void Initialize();
    void Update();
    void Shutdown();

private:
    static AssetSystem& Instance();

    AssetHandle LoadImpl(AssetID id);
    bool IsLoadedImpl(AssetHandle handle) const;

    AssetStorage m_storage;
};

    Systemの状態はinstance memberに保持する。 Engine内部でどこからでも利用したい一部機能のみ、必要に応じてstatic入口を用意する。

    static / non-static とGameへの公開可否は別軸で判断する。

    2. Boundary API

    Game.dllにはSubsystem本体を直接公開せず、Subsystemごとに薄いBoundary APIを置く。

    XxxAPI の実体はEngineが所有し、Engine初期化時に初期化済みの XxxSystem* を設定する。

    class ENGINE_API AssetAPI
{
public:
    void Initialize(AssetSystem* system);

    AssetHandle Load(AssetID id);
    bool IsLoaded(AssetHandle handle) const;
    AssetInfo GetInfo(AssetHandle handle) const;

private:
    AssetSystem* m_system = nullptr;
};

    AssetAPI はSubsystemの実データを所有せず、対応するSystemへの非所有ポインタとGameへ公開する処理だけを持つ。

    void AssetAPI::Initialize(AssetSystem* system)
{
    m_system = system;
}

AssetInfo AssetAPI::GetInfo(AssetHandle handle) const
{
    return m_system->GetDetailedInfo(handle);
}

    System側のstatic入口を利用する処理では、Systemポインタを経由せずstatic APIをそのまま呼んでもよい。

    3. GameEngineAPI

    Engineが所有する各Boundary APIへのポインタを、Game.dllへまとめて渡す。

    struct GameEngineAPI
{
    AssetAPI* m_assets = nullptr;
    GraphicsAPI* m_graphics = nullptr;
    InputAPI* m_input = nullptr;
    AudioAPI* m_audio = nullptr;
    PhysicsAPI* m_physics = nullptr;
    TimeAPI* m_time = nullptr;
    // ...
};

    GameEngineAPI はBoundary APIを所有しない。

    Engine初期化時の流れは以下とする。

    各XxxSystemをInitialize
        ↓
各XxxAPI.Initialize(&XxxSystem)
        ↓
GameEngineAPIへ各XxxAPI*を設定
        ↓
Game.dllをLoad
        ↓
GameRuntimeへGameEngineAPIを渡す

    4. Game.dll側 Facade

    GameコードからはBoundary APIを直接触らせず、Game.dll側にstatic Facadeを置く。

    namespace HestiaGame
{
    class Assets
    {
    public:
        static AssetHandle Load(AssetID id)
        {
            return s_api->Load(id);
        }

        static bool IsLoaded(AssetHandle handle)
        {
            return s_api->IsLoaded(handle);
        }

    private:
        static void Bind(Hestia::AssetAPI* api)
        {
            s_api = api;
        }

        static void Unbind()
        {
            s_api = nullptr;
        }

        inline static Hestia::AssetAPI* s_api = nullptr;
    };
}

    ゲームコードからは次のように利用する。

    auto texture = HestiaGame::Assets::Load(textureID);

    Facade自身はEngineの実データを持たず、注入されたBoundary APIへのポインタのみを保持する。

    6. Hot Reload

    Game.dllのHot Reload時は、FacadeがBoundary APIポインタを保持したままGame.dllを破棄しないようBind / Unbindを行う。

    Game.dll実行
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    Engine側のSubsystem・Boundary API・GameEngineAPIはEngineが所有するため、Game.dllを差し替えても継続して利用できる。

    避けるものの例:

    必要ならBoundary API内部でEngine内部型との変換を行う。

    8. lifecycle APIのアクセス制御

    現段階では Initialize / Update / Shutdown は普通にpublicでよい。

    共通基底の ISystem や ISystemAPI は設けない。 共通化する具体的な必要が出た時点で検討する。

    9. 現時点の設計ルール

    1. Engine内部の本体は XxxSystem とする。
    2. Systemの状態はinstance memberに保持する。
    3. Engine内部で広く使いたい一部機能のみstatic入口を用意する。
    4. static / non-static とGameへの公開可否は別軸で判断する。
    5. DLL境界にはSystem本体を出さず、XxxAPI を置く。
    6. EngineがSubsystemとBoundary APIの両方を所有する。
    7. Engine初期化時、System初期化後に XxxAPI::Initialize(XxxSystem*) で接続する。
    8. XxxAPI は対応するSystemへの非所有ポインタを保持する。
    9. GameEngineAPI は各 XxxAPI* をまとめる非所有ポインタの集合とする。
    10. Game.dll側では HestiaGame::Xxx FacadeにBoundary APIをBindする。
    11. Game ScriptはFacadeを利用する。
    12. Hot Reload時はFacadeをUnbindしてからGameRuntimeとGame.dllを破棄する。
    13. 共通基底 ISystem / ISystemAPI は現時点では作らない。

    ホーム/TransformProcess チャンク並列化設計案

    TransformProcess チャンク並列化設計案

    状態: 検討中・未実装（2026-11-11）

    背景・目的

    HestiaEngineのArchetype + Chunk型ECSにおいて、TransformProcessをチャンク単位で並列化する。 10万EntityでTransform更新とRenderItem更新を合わせて約6ms（個別内訳は未計測）。 現行のチャンクごとのProcess(entities, count, components...)形式は維持する。

    目標は全チャンクを1度だけ並列走査し、Dirty起点判定→サブツリーのWorld行列更新→Dirty解除を完結すること。 起点抽出用の別走査やDirty解除用の再走査は設けない。

    前提条件

    • 親がDirtyになると、全子孫へDirtyを伝播済みの状態で並列更新を開始する。
    • 更新中は新たなDirty設定、親子付替え、Entity削除、チャンク移動をしない。
    • 各チャンクの走査は1 Workerだけが担当する。同一Entityを複数の走査Jobへ割り当てない。
    • 異なるチャンク間に親子関係があってもよい。
    • 親のWorld行列を確定した後に子のWorld行列を更新する。
    • 後段のProcessはTransform更新Jobの完了を待ってから実行する。

    Transformの状態

    enum class TransformState : uint8_t
{
    Clean,
    Dirty,
    Updating
};

    通常の変更受付ではClean → Dirty、更新Process中はDirty → Updating → Cleanと遷移する。 DirtyとUpdatingはいずれも**他のWorkerから見て「親が処理を引き受けるのでスキップ」**する状態。

    更新起点の判定

    各チャンクの並列走査で、まず親の状態を確認する。

    1. 親がDirtyまたはUpdatingなら、その子はスキップ（親側の再帰処理に任せる）。
    2. 親がClean、または親がない場合、自身がDirtyなら更新起点とする。
    3. 起点をUpdatingに変更し、親→子の順でWorld行列を更新する。
    4. 再帰処理の帰りがけに子→親の順でCleanへ戻す。
    開始            更新中                完了
A Dirty         A Updating           A Clean
└ B Dirty       └ B Updating         └ B Clean
  └ C Dirty       └ C Updating         └ C Clean

Cleanへの遷移順: C → B → A

    親がDirtyでもUpdatingでも子側の走査はスキップする。 親がCleanを公開する時点では子孫も更新・解除済みなので、親のDirty解除による二重更新を防げる。 同一Entityの起点判定はチャンク担当Workerに一意であり、再帰更新はその起点の担当Workerだけが行うため、CASでの起点獲得は不要という設計。

    コードイメージ（擬似コード）

    実際のコンポーネント取得API・Transform階層の保持形式・命名に合わせて調整する。

    TransformState GetState(TransformCache& cache)
{
    return std::atomic_ref(cache.m_state)
        .load(std::memory_order_acquire);
}

void SetUpdating(TransformCache& cache)
{
    std::atomic_ref(cache.m_state)
        .store(TransformState::Updating, std::memory_order_relaxed);
}

void SetClean(TransformCache& cache)
{
    std::atomic_ref(cache.m_state)
        .store(TransformState::Clean, std::memory_order_release);
}

void UpdateSubtree(Entity entity)
{
    auto& cache = GetTransformCache(entity);
    // ここに入る時点でcacheはUpdating
    UpdateWorldMatrix(entity);

    for (Entity child : GetChildren(entity))
    {
        auto& childCache = GetTransformCache(child);
        SetUpdating(childCache);
        UpdateSubtree(child);
    }

    // すべての子孫を更新し終えてから解除
    SetClean(cache);
}

void ProcessChunk(Entity* entities, uint32_t count)
{
    for (uint32_t i = 0; i < count; ++i)
    {
        Entity entity = entities[i];
        auto& cache = GetTransformCache(entity);
        Entity parent = GetParent(entity);

        if (IsValid(parent) &&
            GetState(GetTransformCache(parent)) != TransformState::Clean)
            continue;

        if (GetState(cache) != TransformState::Dirty)
            continue;

        SetUpdating(cache);
        UpdateSubtree(entity);
    }
}

    チャンク内のコンポーネント配列が利用できる場合はGetTransformCache等の検索を避ける。

    Atomicの扱い

    • TransformCache::m_stateは普通のenumとして保持し、並列アクセス時にC++20のstd::atomic_refで読み書きする。ECSのSwapRemove等でコンポーネントをコピー・移動できる構造を維持する。
    • 参照が生存する間、同じ状態変数へ非Atomicアクセスを混在させない。
    • std::atomic_ref<T>::required_alignmentを満たす必要がある。
    • SetCleanはrelease、親の状態参照はacquireとし、親のCleanを観測した側に子孫の更新完了を公開する。
    • Dirty → Updatingは、開始前にDirty伝播が完了している前提ならrelaxed Storeで足りる想定。
    • 通常のenumに対する読み書きは、操作が一瞬でも並行するとC++のデータ競合（未定義動作）になる。mutexの「書き込み側だけロック」も不十分。
    • Atomic Load/Storeのみを利用し、mutexとCASは使用しない。ただし、atomic_refが実環境でロックフリーかは実測・確認する。

    TransformProcess (ECS / チャンク並列)
    World行列更新・Dirty解除、変更通知を保持
        ↓

    Mesh / WorldMatrix / WorldAABBなどをRenderItemへ提出
        ↓

    • Meshには共有できるLocal AABB等の形状固有Boundsを保持する。
    • RenderItemは毎フレーム破棄されるため、World AABBをキャッシュするならECSのRenderer側に保持する案。
    • DirtyはTransformProcess中に解除する。後段が更新を知るにはworldChangedまたはWorld行列のVersion等を別途持つ。
    • World AABB更新と描画Viewごとのカリング判定は別責務とする。

    計測・検証項目

    • 約6msの内訳をTransformProcess / MeshRendererProcess / RenderItem提出で分けて計測。
    • 1 / 2 / 4 / 8 Worker、Dirty率0 / 10 / 100%、階層なし / 深い階層を比較。
    • チャンク数・Job粒度・再帰による非連続メモリアクセスの影響を確認。
    • 異なるチャンクにまたがる親子を重点的にストレステストし、二重更新や更新漏れがないか検証する。
    • 1つの巨大サブツリーは1 Workerで再帰処理するため並列性能は伸びにくい。
    • Atomic方式と2フェーズ方式の実測比較は未実施。採否は性能・検証結果で決める。

    Initialize

    bool AssetSystem::Initialize(
    std::string_view databasePath,
    GraphicsSystem* graphics)
{
    m_graphics = graphics;
    s_instance = this;

    if (!m_assetDB.Initialize(databasePath))
        return false;

    if (!GetLoader<Mesh>().Initialize())
        return false;

    if (!GetLoader<Texture>().Initialize(graphics))
        return false;

    if (!GetLoader<MaterialShader>().Initialize())
        return false;

    if (!GetLoader<Material>().Initialize())
        return false;

    return true;
}

    AssetLoader<Texture>のみGraphicsSystemの非所有ポインタを持つ。Loaderが一時画素データを保持するため、TextureのGPU UploadはTextureLoader内で実行する。 AssetLoader<MaterialShader>はDSLのParser/Compile/ReflectionからShaderを構築し、AssetLoader<Material>は依存ShaderをLoad/GetしてMaterialを登録する。どちらもPSOを生成しない。 このInitialize例は4型を有効化した際の到達形。段階的実装中は未実装Loaderの初期化をまだ呼ばない。 Initialize失敗はエラーログを出してfalseを返す程度に留める。

AssetHandle<T> AssetSystem::LoadImpl(std::string_view name)
{
    auto& storage = GetStorage<T>();

    if (auto handle = storage.Find(name); handle.IsValid())
        return handle;

    const AssetInfo* info = m_assetDB.Find(name);
    if (!info)
    {
        // LogError: 未登録の名前
        return {};
    }

    // info->m_type と T の型照合。不一致はエラーログを出して{}を返す。

    // Loaderが内部でRegisterまで行い、Handleを返す。
    return GetLoader<T>().Load(name, info->m_path);
}

    std::string_view name, T* asset)

    // 既存ポインタを所有する。make_unique<T>(asset)は使わない。
    std::unique_ptr<T> owner(asset);

    auto& storage = GetStorage<T>();
    auto handle = storage.Register(name, std::move(owner));

    if (!handle.IsValid())
    {
        // LogError: 名前重複や登録失敗
        return {};
    }

    if constexpr (std::is_same_v<T, Mesh>)
    {
        OnRegistered(handle, *storage.Get(handle));
    }

    return handle;
}

    Texture Loaderの処理例

    役割

    CPU側の静的Meshデータを保持する。頂点属性をStreamごとに分け、Indicesで頂点を参照する。 AssetStorageがunique_ptr<Mesh>で所有し、GraphicsがGPU上のDXMeshを別途所有する。

    MaterialPropertyValue
    Material

    • IDはProperty名から決定的な64bit Hashで作る。同名ならShaderが違っても同じID。生成入口はMaterial::MakePropertyID(name)に統一する。

    ConstantBufferCache

    役割

    型付き正本値からGPU転送形式へ変換したbyte列。Materialにつき1個持つ。 GPUのID3D12Resourceは持たず、Graphicsが描画時にフレーム用Upload領域へコピーする。

    SetProperty(PropertyID, value)
    ↓
MaterialShader::FindProperty(id) → Property Index / Desc
    ↓
型検証
    ↓
m_values[index] = value（正本）
    ↓
CBuffer対象かつ有効Offsetあり
    └─ m_constantBufferCache[offset] へPack
    ↓
m_valueRevision++（値が変わった場合）

描画時:
m_constantBufferCache
    → GraphicsのFrame用CB領域（256byte境界）
    → b2 PerMaterialへBind
    → Pass共通レイアウトとして利用

    MaterialShader

    • byteキャッシュはShader共通Layoutで1回構築し、通常のSetPropertyでは変更箇所だけを更新する。全Propertyを毎DrawでPackし直さない。
    • キャッシュサイズはMaterialShader::GetConstantBufferSize()を使う。D3D12のCBV/GPUアドレス配置時の256byte AlignmentはGraphicsが行う。
    • TextureなどのResource Propertyはbyteキャッシュへ書かない。描画時にm_values内のTexture HandleをGraphicsがBindingする。
    • Reflectionで全Pass未使用のためOffsetが無効なPropertyは、m_valuesへの書き込みだけ行う。未使用化してもMaterial値を失わない。
    • Shaderが変更されたときは新Schemaへ値を移行し、byteキャッシュ全体を再構築する。通常のSet時にShader Revisionが一致していることを前提とする。
    • GPUに実際に転送する領域のFrame寿命・Fenceや、Draw単位のOverrideの一時byteコピーはGraphicsで扱う。

    • ShaderはLoadで重複生成せずCacheから共有する。AssetSystem::Get<MaterialShader>で取得したポインタをMaterialが保持する。
    • SetShaderではSchemaに合わせて既定値を初期化する。別Shaderへの差し替え時に同名・同型の既存Propertyを継承する考え方を維持するが、Reloadとの連携や移行不能時のError状態管理は後回し。
    • Material登録時にはGPUリソースの実体を生成しない。PSOはGraphics側で描画条件に応じて必要時生成する。
    • Shaderへの逆索引vector<Material*>はShader Reloadを実装する段階で検討する。Material自身はShaderを所有しない。

    後回し・未決定

    • 全Property型の詳細なGetter/Setterの網羅、Rangeや色編集等のEditor用Metadata。
    • Shader Reloadと全Material値移行の整合性、逆索引登録・解除。
    • 描画単位のMaterialOverridesとSubmit時のMaterial値確定。
    • 共有Materialを複数Drawで利用する際のCBコピー再利用最適化。

    • 詳細な失敗復旧・Rollback・非同期化。初期はエラーログとbool / 無効Handleで扱う。

    ホーム/戦闘仕様

    戦闘仕様

    状態: 操作・コンボ進行規則は確定。判定・フレーム数・演出強度は未決定。

    基本アクション【確定】

    操作 性質 主な用途
    弱攻撃 素早い広範囲攻撃。雑魚をリアの前方の一点へ寄せる（散らさない） 集敵とコンボ始動
    強攻撃（単発） 広く横薙ぎする1撃。中程度の威力 手早い範囲制圧
    弱 → 弱 → 強 弱で集敵し、広範囲・高威力の強で一掃 雑魚の集団殲滅
    弱 → 強 → 強 より狭い範囲に高い単体火力。最終強は前隙が長い 対ボス
    ステップ 入力方向へ素早く短距離移動。ローリングではない 回避・位置調整
    • 「弱 → 強」でコンボを止められる。ボスの短い反撃機会に対応。
    • ボスは基本的に集敵・通常の吹き飛びに強い耐性を持つ。
    • ステップの距離、無敵時間、各攻撃の具体的な当たり判定は未決定。

    COMBO-001: 攻撃成立と進行【確定】

    • 攻撃判定が出現した時点で攻撃を実行済みとみなし、コンボが進む。空振りでも進む。
    • 判定が出る前にステップでキャンセルした攻撃は不発。ダメージもコンボ進行も発生しない。
    • すべての攻撃はいつでもステップへキャンセル可能。

    COMBO-002: ステップ挿入規則【確定】

    • 各攻撃と次の攻撃の間にステップを1回だけ挟んでも、コンボは継続する。
    • 各成立した攻撃の後に「コンボを維持して使えるステップ1回」が補充される。
    • ステップを連続2回行うとコンボ解除。回避操作そのものは禁止しない。
    • 判定発生前にキャンセルした未成立攻撃は、コンボ進行もステップ権の補充も行わない。
    • 攻撃間の時間切れでもコンボ解除するが、猶予時間は未決定。

    例

    • 継続: 弱 → STEP → 強 → STEP → 強
    • 解除: 弱 → STEP → STEP
    • 判定前キャンセル: 弱(判定前) → STEP は弱攻撃が成立しない。
    • 弱 → STEP → 強(判定前) → STEP では強は成立せず、2回目のSTEPで継続権を消費し切っているためコンボは解除される。

    ATTACK-001: リスクは主に前隙で作る【確定】

    通常: 前隙(短) → 攻撃判定 → 後隙

    対ボス用3段目の強: 前隙(長) ━━━ → 攻撃判定 → 後隙

    • 最終強は長めの**前隙（攻撃が出るまでの時間）**を持つ。過度に重い後隙で硬直させない。
    • 前隙中でもステップキャンセルできるが、大技の判定が出る前ならその攻撃は捨てることになる。
    • ボスの隙が短い場合は 弱 → 強 で切り上げ、長い場合は 弱 → 強 → 強 を狙う。
    • 上記の長短は相対的な方針。フレーム数、派生受付時間、硬直時間は未決定。

    HIT-001: リアの通常被弾【方針確定／数値調整】

    • 基本雑魚の攻撃が命中した場合、リアのHPは通常どおり減少する。
    • 怯み・ノックバック・コンボ中断・移動／ステップの中断は起こさない。入力・攻撃を継続したまま被弾を伝える。
    • 被弾したことは軽い上半身の揺れなどの見た目のリアクション、ヒットエフェクト、SE、HP表示で表現する。攻撃モーションに短い揺れを重ねる方式（Additive等）は実装候補で、演出の強さは未決定。
    • 短い被弾無敵を設け、同時に複数の敵から攻撃されてもダメージが重複しにくいようにする。暫定値は約0.2秒で、一般的な数秒単位の長い無敵は想定しない。
    • 被弾無敵中の追加ダメージは無効。追加の被弾演出・SEも繰り返さない方向とする。ステップによる回避無敵とは別の仕組みとして扱う。
    • ボス・中ボス等の強攻撃による本当の怯み・吹き飛びは、各敵の攻撃を設計する際に別途検討する。強い雑魚の攻撃内容とSAも未決定。

    手触りの検証【優先】

    • 集敵方向と距離が直感的で、敵が1か所に集まって斬れるか。
    • 強攻撃の広さ・ヒットリアクション・吹き飛びが気持ちよいか。
    • 前隙によるリスクを理解でき、ステップキャンセルがストレスなく使えるか。
    • ボスの短い/長い隙の違いが、コンボ選択につながるか。

    • 吹き飛ばした敵の着地・衝突が別の群れ全体の警戒／合流を連鎖的に引き起こす仕組みは、現時点では採用しない。

    • 既存の敵AI設計との関係：SpawnGroup所属は維持し、複数の敵が同時にプレイヤーを認識した場合にCombatGroupへ統合する既存仕様（Enemies.md）は変更しない。群れ間距離・認識範囲・接敵タイミングで、基本的に別群れが同時認識しないように設計する。
    • プレイヤー自身が別の群れへ近づいた場合の連戦・複数群れ同時交戦は否定しない。

    3. 戦闘サイクル【方針確定】

    群れへ接近 → 数百体との交戦 → 短時間で殲滅 → 次の群れへ移動 → 再び殲滅

    戦闘

    • 数百体の密集した敵集団へ突入し、通常コンボで大量の敵を一斉に処理する。
    • 少数の強敵を長く削る遊びではなく、群れの体数と形状がコンボごとに目に見えて減る爽快感を重視する。
    • 撃破数の増加だけでなく、吹き飛ばしによって群れに空間が生じることを視覚的に伝える。

    移動

    • 殲滅から次の群れまでの移動は、戦闘を途切れさせる欠点ではなく、戦闘と非戦闘の緩急として積極的に活用する。
    • 景観を見せる、次に攻略する群れを選ぶ、巨大な群れに再突入する期待を作る時間とする。
    • 群れ同士を常に合流させたり、途切れない連続戦闘を必須にしたりしない。
    • 1群れの殲滅時間・群れ間移動時間は実機で調整する。秒数の確定は行わない。

    • 予兆・攻撃・後隙の時間、リーチ、スフィア半径、追尾旋回速度は実機調整。短い予兆を基本とし、長い溜めは要求しない。

    • 左右はリア本人基準。回転の方向は上から見た向き。

    • 左足を少し前、右足を少し後ろに置く。

    • 主人公リア: 7〜8頭身、金髪ボブ・青い瞳、女性寄りの中性的な若い冒険者。右手に片手直剣、左腕は姿勢のバランスを取る。

    • モーションは1段ずつクリップ化してゲーム内でブレンドする。連続撮影した素材から段ごとに切り出してよい。
    • FBXで自作エンジンへ取り込む想定。Root Motionによる移動制御は使わず、前進・ジャンプ移動などの実移動量はゲーム側で制御する。

    2. コンボ全体

    段 目安尺 基本動作 足運び 終端
    弱1 0.40秒 右上→左下の浅い斜め斬り（20〜30°） 右足を半歩前へ。踏み込みと斬撃を重ねる 剣は左腰付近・剣先は左下

    連結の考え方: 弱1で左下へ振り抜いた剣を弱2で右上へ返す。弱2で右肩〜頭の横にある剣を強3の溜めへ利用する。開始・終了姿勢はブレンドを前提に調整する。

    3. 弱1 — コンパクトな斜め斬り

    動作

    1. 待機中は右腰付近で剣を下げ、剣先は斜め下。ただし弱1のモーションクリップは最初から剣が右上にある姿勢で開始する。待機からの構え直しは短いゲーム内ブレンドで瞬間的に移し、多少のコマ飛び的な不連続を許容する。右肘は軽く曲げ、斬る前に大きく引き直さない。
    2. 右足を小さく前に出すのと同時に、腰→肩→右腕を連動させて振り始める。
    3. 本人基準で右上→左下へ20〜30°程度の浅い斜め斬り。上体はほぼ正面を維持し、終盤に軽く左へひねる程度。大きく身体を回さず、鋭く加速して振り抜く。
    4. 右足の着地と斬撃の終わりをおおむね重ねる。
    5. 剣は左腰付近、剣先は左下へ。勢いを吸収し、弱2でそのまま斬り返せる位置に残す。

    仮タイムライン（合計0.40秒）

    時間 意図
    0.00〜0.06秒 右足を出し始め、重心移動・腰と肩の回転を開始
    0.06〜0.18秒 斬撃の主区間。急加速して右上→左下へ
    0.18〜0.25秒 着地・振り抜き・減速
    0.25〜0.40秒 弱2へつながる位置に収める（長い静止は不要）

    避けたい動き

    • 斬る前に剣を左側へ持っていく、大きく右へ引き直すなどの余計な予備動作。
    • 弱攻撃とは思えない大きな全身回転や、等速でゆっくりした斬撃。
    • 攻撃範囲を広げるためだけに腕を無理に伸ばしきる動き。

    4. 弱2 — 斜め斬り上げ

    動作

    1. 弱1の終端（剣が左腰・左下）から直接開始する。
    2. 足を新たに踏み出さず、腰・肩の回転を切り返しながら、本人基準で左下→右上へ約45°の斬り上げ。
    3. 腰・肩・右腕を連動させ、上体を軽く右へひねりながら切り返し、自然に少し起こす。弱1より上方向への動きを明確にして、敵を浮かせる印象につなげる。膝の伸ばし方や身体の高さは固定しない。
    4. 剣は右肩〜頭の横で止める。大きく頭上へ振り上げない。
    5. この終端を強3の溜め開始姿勢に利用する。

    演出・調整

    • 目安尺は0.40秒。弱1と同様に斬撃の急加速・急減速を優先するが、細かい時間内訳は未固定。
    • 弱1の完全な逆再生に見えないよう、身体の切り返し・剣の高さ・斬り上げ角度に差をつける。
    • 足元が不自然に捻れないよう、腰の回転と足先の向きを撮影後に確認する。

    5. 強3 — 低い跳躍360°回転斬り

    動作

    1. 弱2の終端で剣が右肩〜頭の横にある状態から、剣を右肩後方へ軽く引き、身体を沈めて溜める。
    2. 左足を前へ踏み込み、地面を蹴って低く跳躍。高く跳ぶのではなく、両足が短く浮く程度の低空回転。
    3. 上から見て反時計回りに360°回転。剣を身体の外側へ広げながら周囲を薙ぐ。最初から腕を伸ばしきる必要はなく、回転の中で自然に振り抜く。
    4. 約270°は空中で回り、着地しながら**残り約90°**を斬る。角度は動きの目安で、厳密に演じる必要はない。
    5. 着地に合わせて重心を左へ沈め、左膝を曲げ・右脚を横へ伸ばすサイドランジへ。右膝は伸ばしきらず余裕を残す。
    6. 剣を胸〜腰の高さから左下へ振り抜き、最後は正面を向いた低い姿勢で終える。

    仮タイムライン（合計0.65秒）

    時間 意図
    0.00〜0.25秒 左足を踏み込み、沈み込み・剣を右肩後方へ引いて溜める
    0.25〜0.32秒 低く蹴り出し、回転開始
    0.32〜0.52秒 空中で約270°回転しながら斬る
    0.52〜0.65秒 着地・沈み込みとともに残り約90°を斬り、左下へフィニッシュ
    • 斬撃は空中回転中から始める。着地してからだけ斬る動作にはしない。
    • 接地した足を固定して強引に360°捻らない。足先や接地タイミングは自然な範囲で調整する。
    • 強3終了後の後隙0.35秒はゲームロジック側で管理し、アニメーション終了後はIdleへブレンドする方針。
    • 尺0.65秒はかなり速い想定。撮影・調整で無理が出れば0.70〜0.80秒程度への変更も検討可能。現段階では仮のまま。

    6. 撮影・モーション化・編集方針

    1. 最初は弱1→弱2→強3を通しで演じると、重心と足運びのつながりを作りやすい。必要なら各段を単独でも撮る。
    2. 撮影中は秒数に無理に合わせない。斬撃方向・足運び・大まかな溜めと加速を守り、自然に動ける速さで撮影する。
    3. 取得した動画から各段をトリミングし、動きの再現に使う。実写→Viggle直接と実写→Muse→Viggleの品質・対応機能は未検証なので、後で小さく比較する。
    4. 抽出したモーションはBlenderで姿勢、開始・終端、リタイミング、速度カーブ、剣の軌道、接地を補正する。映像を先にリタイミングする方式も比較候補。
    5. 各段をFBXとして出力し、ゲーム内でブレンドする。前進や移動量はアニメーション内のRoot Motionに頼らず、ゲーム側で別途制御する。
    6. 撮影で剣状の小道具を使う場合は柔らかく軽い安全なものを使用し、低い跳躍・回転は広く滑りにくい場所で無理なく実施する。

    • 弱1→強2→強3を通しで撮影する。弱1は弱弱強の共通クリップを利用する。

    狙い

    コンボを経由せず出せる、前方広範囲・中威力の水平薙ぎ払い。弱1の浅く素早い斜め斬りに対し、右肩で見える溜め→一気に踏み込む→胸の高さの大きな水平斬りで明確に差別化する。身体は360°回転させず、腰と肩を大きく回す。

    動作

    1. 待機は剣を右腰・剣先斜め下に下げた基本構え。
    2. 剣を右肩付近へ引き上げて軽く溜める。この動きは弱1と異なり、省略せずに見せる。
    3. 溜めの後、左足を一気に前へ踏み出し、腰と肩を使って右→左へ大きく水平に薙ぎ払う。剣は胸付近の高さを通す。着地と斬撃の勢いをおおむね合わせる。
    4. 最後は剣を身体の左側まで大きく振り抜き、上体も左へひねった姿勢で終える。正面向きのまま左前方で止める案ではない。
    5. 振り抜いた姿勢で一瞬静止し、その後に構えへ戻す。静止時間は未固定。攻撃成立後はステップキャンセル可能。

    足運びは撮影で最終決定

    • 左足踏み込みを仮採用。基本構えでは左足が少し前なので、同じ足をさらに大きく前へ踏み出す動きを撮影で検証する。
    • 比較案は右足踏み込み。身体のひねり・接地・斬撃の勢い・自然さを優先して決める。
    • 「溜めてから一気に踏み込む」タイミング方針は採用。溜め始めと同時に足を出す案ではない。
    • 足の入れ替えや膝の曲げ角度など、撮影で自然に処理できる細部は事前固定しない。

    制作時の留意点

    • 単発強は水平・大きい・溜めが見える。弱1は浅い斜め・コンパクト・素早い。
    • 空中360°回転を伴う強3-1とも別物。単発強は地上で踏み込みながら広く薙ぐ。
    • 尺、判定発生フレーム、溜めや静止の秒数は未固定。判定・キャンセル規則は Combat.md に従う。
    ホーム/リア 攻撃モーション — 撮影チェックシート

    リア 攻撃モーション — 撮影チェックシート

    共通仕様 ｜ 弱→弱→強 ｜ 弱→強→強 ｜ 単発強

    右手に剣。左右は自分から見た方向。 速度・厳密な秒数より、足運びと斬撃方向・開始/終端を優先。

    共通：基本構え

    • 左足を少し前、ほぼ正面向き（自然な程度に左肩前）。
    • 剣は右腰で下げる、剣先は斜め下。
    • 弱1は剣が右上にある位置から撮影してよい。待機からの移動は短いゲーム内ブレンドで省略する。

    弱 → 弱 → 強

    • 弱1：右足を半歩前へ。右上→左下の浅い斜め斬り（20〜30°）。上体はほぼ正面、軽く左へ。終わりは左腰・剣先左下。
    • 弱2：追加踏み込みなし。左下→右上へ約45°の斬り上げ。上体を軽く右へ切り返す。終わりは右肩〜頭の横。
    • 強3-1：左足を踏み込み、低い跳躍で上から見て反時計回り360°。空中約270°、着地しながら約90°。最後は左膝を曲げた低いサイドランジ、剣は左下。
    • 目安尺：弱1約0.4秒 / 弱2約0.4秒 / 強3-1約0.65秒（仮）。撮影では厳密に合わせない。

    弱 → 強 → 強

    • 弱1：上記の共通クリップ。右足を半歩前へ。
    • 強2：追加踏み込みなし。右足前のまま腹部付近を低く突く。上体は軽く前傾。突いた剣を引き戻しながら頭上へ。
    • 強3-2：剣を頭上へ振り上げる途中に左手を添え、頭上で両手持ちに。身体は高く、一瞬静止。左足を大きく踏み込み、両手で地面へ叩きつける縦斬り。
    • 終わり：左膝を深く曲げて低く前傾。剣を地面で一瞬止め、引き上げる。地面への強打は安全な演技・編集で再現。

    単発強

    • 右肩へ剣を上げて軽く溜める。弱1と違って振りかぶりを見せる。
    • 溜めた後に一気に踏み込み、胸の高さを右→左へ大きく水平薙ぎ払い。360°回転しない。
    • 左足踏み込みは仮。撮影では右足踏み込みも比較する。
    • 終わり：剣を身体の左側まで振り抜き、上体も左へ。短く静止して戻る。

    撮影前

    • 全身と足先が画面に入る。周囲・床の安全を確認する。
    • 剣状の小道具は軽く安全なものにする。地面を強打しない。
    • それぞれのコンボを通しで撮り、必要に応じて段ごとに切り出す。
    • 余計な細部を無理に演じず、自然な速さ・身体の動きを優先する。

    後で調整: Blenderで開始/終端、速度、接地、剣の軌道を補正。ゲーム内のモーションブレンド・判定・ステップキャンセルは実装側で扱う。

    ホーム/ステージ制作 共通仕様

    ステージ制作 共通仕様

    • 対象：LEIR（仮）／3D無双系アクション
    • 状態：大枠の制作方針は確定。技術詳細・実装方式はCodex Aで調査・設計
    • 更新：2026-11-05
    • 個別ステージ：草原／遺跡（後日）

    1. 目的・共通のゲームデザイン【確定】

    • 草原、遺跡など、景観の異なる複数の独立したステージを制作する。
    • 違いの中心は景観・雰囲気。基本戦闘の構造は共通とし、現段階ではフィールドギミックを要件にしない。
    • 多数の敵を集めて斬り払う無双アクションを妨げないこと。移動しやすさ、敵の集団移動と吹き飛ばし、カメラの見通しを重視する。
    • 初期は1部屋で基本戦闘を検証する。ステージごとの個別地形・寸法・世界観・装飾・シェーダーの選択は個別仕様に定める。

    2. アセット構成・再利用【確定／具体的な分割数は仮】

    • Blender完成シーンを形状と配置の正本とする。ゲーム側で手作業による再配置を必要としないことを目指す。
    • 1つの巨大な結合FBXにはせず、十数〜数十種類程度のFBXアセットを組み合わせる。数は制作上の仮目安で、固定の上限・下限ではない。
    • 分類は次の3つを基本とする。
    分類 役割と分割方針
    Terrain ステージ専用の比較的大きな地形メッシュ。戦闘地形、外周、必要な中景・遠景など。原則1〜数個程度を基本に、自然な起伏を優先して無理なタイル化をしない
    Structure 大きな構造・地形パーツ。例：岩壁、川岸の要素、遺跡の壁・柱。必要に応じてモジュール化・再利用する
    Prop 木・岩・草・花・装飾品など。同じFBXを複数インスタンスで参照し、Transformだけを変えて配置する
    • Propは配置数分のFBX複製を出力しない。Structureも必要に応じて再利用する。
    • 共有アセット＋ステージ専用アセットを併用する。複数ステージで使う木・岩などは共通の参照先にまとめ、Terrainや固有の建造物などは各ステージに持たせる。
    • ディレクトリ、命名、ステージ間参照の具体規約はCodex Aで決める。

    3. Blender → FBX・配置JSON【方針確定】

    1. Blender上でアセット制作と配置を行い、完成シーンを確認する。
    2. 各ユニークアセットをFBXとして出力する。
    3. Blenderシーンから、各インスタンスのアセット参照とTransform（位置・回転・スケール）の組をJSONへ出力する。
    4. ゲームエンジンはFBX群とJSONを読み、Blenderでの配置を再現する。
    • 複数の配置が同じメッシュ・FBXを共有できる設計とする。
    • JSONは将来的なインスタンス単位のマテリアル上書きや、コリジョン参照などの情報を扱えるようにする。
    • JSONスキーマ、座標系・単位系、回転形式、ピボット、親子Transform、パス解決、エクスポートの自動化は未決定。Codex Aで既存のエンジン仕様を調査する。
    • Blenderとエンジンで同じ位置・向き・スケール・参照アセットになることを検証対象とする。

    4. マテリアル・シェーダー【方針確定】

    4.1 サブメッシュ／マテリアル

    • 1つのFBXに複数マテリアルを許容する。エンジンはUnityと同様にサブメッシュ単位でマテリアルを割り当てられる想定。
    • 無理なアトラス化や一律の1マテリアル化をしない。統合が必要かは性能・アセットごとに後から判断する。
    • テクスチャは必要に応じてFBXとは別リソースとして管理・共有する。
    • 既定マテリアルだけでなく、配置インスタンス単位のマテリアル上書きにも対応できる情報設計を目指す（通常は共通割り当てを利用）。

    4.2 識別情報を優先

    • エンジン側のマテリアルシリアライズ形式は未決定。Blenderのマテリアルを直接ゲーム用マテリアルとして取り込むことは必須にしない。
    • 出力時には少なくともマテリアルの識別子、種類（用途・描画分類など）、対応するマテリアルスロット／サブメッシュを判別できる情報を残す。
    • マテリアルIDの永続化や名称変更への耐性、種類の分類値、テクスチャの参照方法はCodex Aで具体化する。単に表示名だけを恒久IDにするとは確定しない。
    • 同じメッシュを参照していても配置ごとに異なるマテリアルを選べる余地を確保する。

    4.3 シェーダーとBlenderプレビュー

    • 最終的なシェーダー・描画表現はゲームエンジン側で実装する。自由にシェーダーを書ける想定。
    • Blenderでは簡易マテリアル＋テクスチャ表示ができれば十分。ゲーム側との完全な見た目の一致、BlenderノードのHLSL変換、複雑なシェーダー再現は要求しない。
    • Terrainのシェーダーはステージ固有に選択する。マスクブレンドが必要なステージも、通常のテクスチャだけでよいステージもある。全Terrainを単一の共通シェーダー／マスク形式に固定しない。
    • 水面・植物・岩などの用途別シェーダーの詳細仕様やリソースの紐付けはCodex A／エンジン実装段階で決める。

    5. コリジョン【方針確定】

    • 描画メッシュとコリジョン用メッシュを分離し、簡略化した衝突形状をBlender上で作成・配置する。
    • Terrain・複雑なStructure： 表示メッシュを基に自動簡略化し、必要な部分を手動調整する方針。
    • 単純なProp： Box / Sphere 等のプリミティブ、または簡略化メッシュを使う。草・花などの小さな装飾は原則コリジョンなしを想定。
    • 見えない壁： 必要に応じて専用の簡略化メッシュを手作業で用意する。景観の輪郭に完全一致させる必要はない。
    • 描画とは別にコリジョンデータを出力し、ゲーム側で対応付けられるようにする。具体的なファイル形式、物理エンジンへの登録、衝突属性・配置の管理方式はCodex Aで決める。

    6. Codex Aで調査・詳細設計する事項【未決定】

    • 既存エンジンのFBX・サブメッシュ・テクスチャ・マテリアル・コリジョンの対応状況。
    • Blenderのシーン構成、FBXの分割／原点ルール、座標変換・ピボット・単位、エクスポータ仕様。
    • FBX参照／Transform／マテリアルの識別と上書き／コリジョン対応を記録するJSONスキーマ。
    • シェーダー種類の分類とID管理、ゲーム側リソースへの対応付け（マテリアルの実データ形式は未決定）。
    • コリジョンの簡略化・編集・出力とランタイム登録、物理判定の範囲。
    • Prop再利用時の描画最適化、LOD、テクスチャ予算など。事前に過度なアトラス化・個数固定をしない。
    • Blender完成シーンに対する出力結果の再現性、参照切れ、アセット重複、必要なON/OFF切替などの検証方法。
    • Codex BのGoal実行用の成果物・完了条件・検証手順。

    この文書は制作方式の共通要件であり、技術実装の詳細仕様・Goalプロンプトではない。個別ステージの地形・演出・マテリアル表現などはそれぞれの仕様書を参照する。

    ホーム/草原ステージ 要件整理

    草原ステージ 要件整理

    • 対象作品：LEIR（仮）／3D無双系アクション
    • 状態：景観・地形の方向性は確定。数値・具体的な美術設計・制作詳細は仮／未決定
    • 更新：2026-11-05
    • 共通制作仕様：Stage_Common.md（Blender／FBX／JSON／アセット・マテリアル・コリジョン管理）

    1. 位置付け

    • 草原は遺跡とは別の独立したステージとして制作する。
    • まず草原の戦闘部屋1つを作り、移動・集敵・吹き飛ばしなどの基本戦闘を検証する。
    • ステージごとの変化は主に景観・雰囲気。フィールドギミックは現時点で考えない。
    • 大量の敵をなぎ倒せる広さと視界を優先しながら、自然な草原の景観を作る。

    2. 世界観・ビジュアル【方向性確定】

    • 明るく爽やかな王道ファンタジーの草原。新緑・青空・草花を基調とする、アニメ調／スタイライズド3D。
    • 少しだけファンタジーらしい個性を含める。ただし、特定の発光植物・巨大樹・独特な遠景等のモチーフは指定しない。具体的な意匠はCodexのセンスに任せる。
    • 開放感を重視するが、戦闘可能エリアの外の中景・遠景は制作量を抑える。

    3. 戦闘可能エリア【基本方針確定／寸法は仮】

    • 直径・代表幅の仮目安：70〜100m程度。まず約80m前後を想像するが、プレイヤーの速度、敵の密集・スポーン、カメラを見て調整する。
    • 輪郭は自然な不規則形。極端なくびれや、戦闘の邪魔になる狭い場所は避ける。
    • 中央を含めて完全な平地ではなく、移動・集団戦・吹き飛ばしを妨げない緩やかな起伏を設ける。
    • 中央には広い草地を残し、大きな岩・倒木・木立などは主に外周寄りに置く。

    4. 外周・川【基本方針確定】

    • 岩場・木立・丘／段差・川を混合して、景観に沿った自然な境界を作る。
    • 川は細い小川ではなく、橋が必要に見える程度の幅があるものを想定。少しカーブさせて、外周の約1/4〜1/3を進入不可エリアの表現に利用する。
    • 川岸は少し落差のある地形とし、水際に降りられないことを納得させる。岩や草で不規則な輪郭を作る。
    • 残りの境界は岩場、木立、斜面などでつなぎ、全周を同一の景観要素で囲まない。
    • ある程度の見えない壁は許容する。見た目の外周に完全に合わせて衝突形状を複雑化させる必要はない。
    • 境界の簡略化コリジョンや見えない壁の作り方は共通仕様に従い、具体配置はCodex Aで設計する。

    5. 地面・道【基本方針確定】

    • 草地を主体に土・露出した岩肌などの変化をつける。
    • 草原固有の地表表現として、マスクテクスチャによる草・土・岩肌などのブレンドを希望する。
    • 緩やかに曲がる一本道を戦闘エリアの中心から少し外れた位置に通し、中央の広い草地を保つ。
    • 道は整備された直線道路ではなく、人や馬車が通って踏み固められた土の道。幅や境界に自然な変化をつける。
    • 道の両端は丘・木立の奥、または岩場・崖に沿って曲がる先で視界から消えるようにする。橋や川向こうへの接続は前提にしない。
    • マスクブレンドの最終的なシェーダーはゲームエンジン側で制作する。Blenderではテクスチャによる簡易プレビューでよい（共通仕様）。

    6. 植生・環境オブジェクト【方向性確定】

    • 密度は中程度（B案）。草・花・小岩・踏み荒らし・外周寄りの倒木や大岩などをバランスよく配置する。
    • エリア内部を障害物で埋めず、敵の群れとプレイヤーの移動を優先する。
    • 細かな草花はまず単体Propアセットを多数配置する。後からシェーダー表現と比較できるようにする。
    • 草花はまとめて表示ON/OFF可能な構成を目指す。
    • 草花OFFでも地面テクスチャだけで最低限の景観が成立するのが望ましい。
    • 同一Propの使い回しとTransform違いの配置、共通／専用アセットの仕分けは共通仕様に従う。

    7. 中景・遠景【方向性確定】

    • 戦闘エリア外の丘や木立、岩で近い地形の続きを表現し、見せたくない場所を自然に遮蔽する。
    • 遠くに山並みや空などを見せて、開放感と制作コストを両立する。
    • カメラが周囲を向いても破綻しにくい構成を目指す。具体的な遠景表現はCodex Aで調査・提案する。

    8. Codex Aへの引き継ぎ【未決定】

    • 川・川岸・戦闘地形・外周・道の具体的な形状と配置。
    • 草原固有の地面マスク、必要なテクスチャ、エンジン側でのブレンド表現。
    • 草花・岩・樹木などの種類数、見栄えと再利用性、表示ON/OFFの実現方法。
    • プレイヤー移動、敵の群れ、吹き飛ばし、カメラに対する空間の検証。
    • 明るいファンタジー草原としての美術提案。細部の装飾モチーフは事前に固定しない。
    • 出力・配置・衝突・マテリアルの一般的な制作方式はStage_Common.mdを参照し、重複して別仕様にしない。

    6. 建築様式と崩壊表現【方向性確定】

    • 双塔の門・アーチ列柱・東屋・庭園など、元モデルの主要な建築物の種類と大まかな配置を維持する。
    • 双塔の門や主要ランドマークは形が読み取れる程度に残す。一方で外周の回廊・列柱・壁・橋などには欠け、倒壊、破断、瓦礫を加える。
    • 元モデルの列柱・アーチ・門の寸法や細部は盲目的に流用せず、石材の厚さ、構造的な納得感、装飾の統一感を改善する。
    • 柱・アーチ・欄干・縁取りなどは繰り返し使える単位を共通化し、破損／非破損のバリエーションを必要な範囲で設ける。
    • 破損の具体的な形状・瓦礫の置き方・装飾パターンなど、美術的な細部は事前に過度に固定しない。

    9. アセット分割とBlender → ゲーム連携【重要・共通仕様に準拠】

    • Blender完成シーンを形状と配置の正本とする。独立したアセットを適切な単位で管理・書き出し、配置JSONで元シーンを再現できるようにする。
    • Terrain / Structure / Prop を基本分類とする。
    区分 遺跡ステージでの対象例 分割の方向性
    Terrain 浮遊島の地形・岩肌・外周地形 ステージ固有の比較的大きなメッシュ。無理なタイル化をしない
    Structure 円形広場・床の装飾・水路の縁・双塔の門・アーチ・列柱・橋・東屋 固有形状と再利用できる建築モジュールを適切に分ける

    • 何でも個別FBX化しない。同じ柱でも、構造的に一体として扱った方がよい飾りまで必ず分離する必要はない。

    • 1 FBX内の複数サブメッシュ・マテリアルを許容する。過度なアトラス化や全マテリアル統合は行わず、実際の品質・性能要件を見て判断する。
    • 水面・滝は、石造構造物と別に表示・マテリアルを管理しやすい形にする。実装上の分類・出力方式の詳細はCodex Aで決める。
    • 描画メッシュとコリジョンは分離する。アリーナ外周の見えない壁、床、主要建築物等に簡略化した衝突形状を用いる。具体形式・物理挙動は共通仕様に従い調査する。
    • アセットの具体的な種類数・分割数・ポリゴン予算はここでは固定しない。元FBXの状態とエンジンの制約を調査した上で設計する。
